# Taste
- When fixing a compile/type error in code they wrote themselves, wants only the error fixed — no refactors, reformatting, or other changes to their code ("solve those problems otherwise dont change my code"). Confidence: 0.95
- When they mark a block of their own code as off-limits, expects it preserved verbatim even when it contains real bugs — wants the fix applied elsewhere (e.g., adding a `name` to the field so their `FormData` code works, or deriving the wanted value around their `await getMenu(id)` call) and any remaining issues in the frozen block reported, not rewritten. Confidence: 0.9
- Does not want the assistant to over-reach: expects ONLY the stated requirement implemented and nothing else touched — wants minimal, scoped changes ("only implement this requirement dont touch or implement other codes"), and no unsolicited scaffolding of extra files, routes, or components beyond the minimal fix (stopped a fix that created a whole dashboard sidebar + placeholder route pages). Confidence: 0.85
- Prefers changes made in place in the existing file/repo over language migrations or restructuring: when offered a TypeScript modular rewrite (the recommended option) versus a minimal fix, chose to keep the existing JavaScript `index.js` and fix it where it is. Confidence: 0.6
- When they ask a question rather than request work — to "check"/diagnose a problem, or just where something lives — wants the answer only (root cause plus explanation, or the file/route path) with no code changes; they apply the fixes themselves ("dont implement anything just check that is the error happening from here, then why"; "dont modify just say"; "give me the path, dont touch or implemet anything"). Confidence: 0.85
- Prefers the simplest implementation that meets the need: plain controlled React state over heavier abstractions/libraries (explicitly said "do not complicate the form data and overall logic" when asked for a form, rejecting react-hook-form + zod in favor of shadcn primitives). Confidence: 0.7
- Wants domain types kept in a shared/central location and repeated styles or duplicated markup factored into reusable components instead of copy-pasted across files (DRY). Confidence: 0.8
- Expects refactors and improvements to be non-breaking and additive — wants a step-by-step plan (each step standing on its own) rather than changes that alter existing exports or behavior. Confidence: 0.75
- Keeps project requirements in a `docs/` folder and expects the assistant to read those specs up front, before implementing any feature, so it has the full picture — and will halt an in-progress fix to demand the requirements be checked first ("firstly check the requirement"). Confidence: 0.8
- Wants an approval gate before implementation: asks for a complete step-by-step workflow (step 1, step 2, …) mapped to the requirements doc with nothing omitted, then picks which steps the assistant should modify or implement — no code written until then. Hands requirements over one step at a time, expects each part checked carefully against the actual code, and wants to be asked before any modification is made rather than deciding for themselves. Confidence: 0.8
- Separates UI work from data wiring: wants the interface implemented now with placeholder/dummy data (marked as such) and will hook up the real data source later (e.g., building the payment UI now while explicitly deferring the Stripe checkout integration). Confidence: 0.7
- Prefers Next.js App Router pages to be Server Components — reads the session server-side (`auth.api.getSession` + `headers()`) and does the data fetch on the server, pushing interactivity into child client components — rather than making the page a client component with `useSession`/`useEffect`. Confidence: 0.65
- Wants their existing, working code left untouched: don't modify it until it actually errors, while still making whatever changes are required to fulfill the stated requirement ("dont change my code until it gives error, modify as much you need to fulfill requirement"). Confidence: 0.8
- The requirements doc is the source of truth: when the existing code conflicts with the spec, wants the spec followed literally rather than the assistant's own reading, and does not want to be asked to choose on points the requirement already answers ("follow as said on the requirement"). Confidence: 0.7
